# I-Dentity Backend

## Стек

- **Java 17, Spring Boot 3.5** — язык и фреймворк приложения

- **Spring Security, Spring Data JPA (Hibernate)** — безопасность, авторизация и работа с базой данных

- **PostgreSQL 15, Liquibase** — хранение данных и управление схемой БД

- **RabbitMQ 4.2** — асинхронная обработка задач

- **SeaweedFS 4.52, AWS SDK v2** — хранение изображений через S3 API

- **Apache Tika, Caffeine** — проверка формата файлов и ограничение частоты запросов

- **Springdoc OpenAPI (Swagger)** — документация API

- **Gradle, Docker Compose, Make** — сборка приложения и управление инфраструктурой

- **Lombok, JUnit 5, JaCoCo** — сокращение шаблонного кода, тестирование и оценка покрытия тестами



## Адреса

Если использовать значения из `.env.example` без изменений:

- **Backend:** http://localhost:8080
- **Swagger UI:** http://localhost:8080/swagger-ui.html
- **OpenAPI JSON:** http://localhost:8080/v3/api-docs
- **RabbitMQ Management:** http://localhost:15672
- **SeaweedFS (S3 API):** http://localhost:8333



## Запуск

Нужны **JDK 17**, **Docker с Docker Compose** и **Make**.

1. В корне проекта создать файл `.env` и скопировать в него содержимое `.env.example`

2. Запустить Docker

3. Открыть терминал в корне проекта и выполнить команду:

   `make up`

4. Убедиться, что все три контейнера — `postgres`, `rabbitmq` и `seaweedfs` — успешно запущены:

   `make ps`

5. Запустить бэкенд через терминал в корне проекта следующей командой:

   `./gradlew bootRun`


Для самой проверки изображений необходимо отдельно запустить ML-сервис.


**Конфигурации Docker Compose** находятся в каталоге **deploy/** в корне проекта.


**Управление контейнерами:**

- `make stop` — остановить контейнеры
- `make up` — запустить контейнеры
- `make down` — остановить и удалить контейнеры, а также созданную сеть, сохранив тома с данными
- `make logs` — посмотреть журналы работы контейнеров

Все команды управления Docker Compose находятся в файле `Makefile` в корне проекта.



## API

### Авторизация и пользователи

- `GET /auth/csrf` — получение CSRF-токена для защищенных запросов. Авторизация не требуется

- `POST /auth/sign-up` — регистрация пользователя. Принимает JSON с `username`, `email` и `password`. Возвращает данные пользователя (`username`, `email`, `role`) и устанавливает куки сессии. Авторизация не требуется

- `POST /auth/sign-in` — вход в систему. Принимает `username`, `password` и необязательный `rememberMe`. Возвращает данные пользователя и устанавливает куки сессии. Авторизация не требуется

- `GET /auth/me` — получение данных текущего пользователя (`username`, `email`, `role`). Требуется авторизация

- `POST /auth/logout` — завершение текущей сессии и удаление куки

- `POST /auth/reset-password` — изменение пароля. Принимает `username`, `newPassword`, `confirmationCode`. Завершает старые сессии и создает новую. Требуется авторизация

- `PATCH /users/me/email` — изменение почты. Принимает `email` и `currentPassword`. Возвращает `204 No Content`. Требуется авторизация


### Проверка изображений

Оба эндпоинта требуют авторизации.

- `POST /images/upload` — загрузка изображения для проверки. Принимает `multipart/form-data` с полем `file` (JPEG/PNG, до 5 МБ). Возвращает `202 Accepted` с `imageId` и `status: PENDING`
- `GET /images/{imageId}/result` — получение состояния и результата проверки по идентификатору изображения. Возвращает `imageId`, `status`, `predictedClass`, `classDescription`, `fakeProbability`, `error`. Пользователь может получать результаты только своих изображений

Возможные статусы: `PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`.

При успешном завершении проверки `predictedClass` равен `0` (Real) или `1` (Fake), а `fakeProbability` содержит вероятность подмены лица от 0 до 1. При ошибке поле `error` содержит ее код.


### Администрирование

Все перечисленные ниже эндпоинты доступны только пользователям с ролью `ADMIN`.

**Изображения:**

- `GET /admin/images/all` — получение списка изображений с пагинацией
- `GET /admin/images/{id}` — получение информации об изображении (`id`, `filepath`, `uploadDate`)
- `GET /admin/images/exists/{id}` — проверка существования изображения. Возвращает `true` или `false`
- `GET /admin/images/search` — поиск изображений по `filepath` или `uploadDate`

**История проверок:**

- `GET /admin/verification-history/all` — получение истории проверок с пагинацией
- `GET /admin/verification-history/{id}` — получение подробной информации о проверке, включая данные пользователя на момент ее выполнения
- `GET /admin/verification-history/search` — поиск записей по `imageId`, `userId`, `verificationDate` или `result`
- `DELETE /admin/verification-history/delete/{id}` — удаление записи истории проверки

Для списков и поиска используются параметры `page` (по умолчанию `0`) и `size` (по умолчанию `20`, максимум `100`). Ответ содержит `pagination` и `items`.

Ошибки API возвращаются в формате `statusCode`, `message`, `data`.



## Авторизация

Авторизация реализована через **сессии и куки**.

При регистрации или входе сервер создает случайный токен сессии и передает его в куки `IDENTITY_SESSION` с флагами `HttpOnly` и `SameSite=Lax`. В PostgreSQL хранится только SHA-256-хеш токена. Пароли пользователей хранятся в виде BCrypt-хешей.

Обычная сессия действует **2 часа**, при входе с `rememberMe: true` — **14 дней**. При выходе сессия отзывается, просроченные записи периодически удаляются.

Для защиты от CSRF перед запросами `POST`, `PATCH`, `PUT` и `DELETE` необходимо получить токен через `GET /auth/csrf` и передать его в заголовке `X-XSRF-TOKEN`. Браузер при этом должен отправлять куки вместе с запросами.

При регистрации пользователю назначается роль `USER`. Административные методы доступны только роли `ADMIN`.

Для входа, регистрации и изменения пароля используется ограничение частоты запросов через Caffeine.



## Асинхронная обработка изображений

Проверка изображений выполняется асинхронно через RabbitMQ.

Каждая задача проверки хранится в PostgreSQL и имеет один из четырех статусов:

- **PENDING** — задача ожидает обработки или повторной попытки

- **PROCESSING** — задача выполняется обработчиком

- **COMPLETED** — изображение успешно проанализировано, результат сохранен

- **FAILED** — проверка окончательно завершилась ошибкой


**Процесс обработки:**

1. **Загрузка изображения.** Клиент отправляет файл с изображением через `POST /images/upload`. Бэкенд проверяет изображение, сохраняет его в **SeaweedFS (S3)** и создает в PostgreSQL задачу проверки со статусом `PENDING`. Задача связана с загруженным изображением через его идентификатор `imageId`

2. **Отправка задачи в очередь.** Планировщик `ImageVerificationTaskDispatcher` каждые 2 секунды ищет в PostgreSQL задачи со статусом `PENDING`, для которых наступило время обработки (`nextAttemptAt` меньше или равно текущему времени) и которые еще не отправлялись в очередь, либо с момента последней отправки прошло более 45 секунд (`lastDispatchedAt`). Для каждой такой задачи через `RabbitMqVerificationTaskPublisher` в очередь RabbitMQ отправляется сообщение с `imageId`

3. **Получение и выполнение задачи.** `RabbitMqVerificationTaskListener` получает сообщение из очереди RabbitMQ и передает `imageId` в обработчик `ImageVerificationProcessor`. Обработчик находит соответствующую задачу в PostgreSQL, переводит ее в статус `PROCESSING`, загружает изображение из S3 и через `NeuralNetworkClient` отправляет его в ML-сервис

4. **Получение и сохранение результата.** ML-сервис анализирует изображение и возвращает бэкенду результат классификации (Real/Fake) и вероятность подмены лица. `ImageVerificationProcessor` получает этот ответ, после чего `ImageVerificationTaskService` сохраняет результат в PostgreSQL, создает запись истории проверки через `ImageVerificationWriter` и переводит задачу в статус `COMPLETED`


**Получение результата клиентом**

Сразу после успешной загрузки изображения и создания задачи бэкенд возвращает ответ `202 Accepted`, содержащий `imageId` и статус `PENDING`. Это означает, что изображение принято на проверку, но анализ еще не завершен.

Клиент использует полученный `imageId`, чтобы периодически отправлять `GET /images/{imageId}/result` и получать текущее состояние задачи или итоговый результат.


**Обработка ошибок**

При временной недоступности ML-сервиса или S3-хранилища задача переводится из `PROCESSING` обратно в `PENDING`. Через `nextAttemptAt` устанавливается время следующей попытки, после наступления которого планировщик снова отправит задачу в RabbitMQ. Всего предусмотрено до трех попыток обработки.

Планировщик `ImageVerificationTaskDispatcher` также проверяет наличие задач, зависших в статусе `PROCESSING` более 120 секунд. Если количество попыток меньше трех, он возвращает такую задачу в `PENDING`, сбрасывает время начала обработки и разрешает повторную отправку в RabbitMQ. Если попытки исчерпаны, задача переводится в `FAILED` с кодом `PROCESSING_TIMEOUT`.

Если при обработке возникает ошибка, для которой повторные попытки не предусмотрены (например, отсутствие лица на изображении), либо исчерпаны все три попытки, задача также переходит в `FAILED` с соответствующим кодом ошибки.

Статусы `COMPLETED` и `FAILED` являются конечными: после перехода в любой из них задача больше не отправляется в RabbitMQ и не обрабатывается повторно.



## Историчность пользователя

Текущие данные пользователя хранятся в таблице базы данных `users`, а их история — в `user_version`.

При регистрации создается первая версия пользователя. При изменении почты текущая версия закрывается и создается новая. Каждая версия содержит номер, данные пользователя, причину изменения и период действия (`validFrom`, `validTo`).



## Сущности JPA

- **User** — текущие данные пользователя: имя, почта, хеш пароля и роль
- **UserVersion** — история изменений данных пользователя с указанием периода действия каждой версии
- **AuthSession** — сессия пользователя: хеш токена, владелец, время создания и истечения
- **Image** — информация о загруженном изображении: идентификатор, путь к файлу в S3 и дата загрузки
- **VerificationTask** — задача проверки изображения: владелец, статус, количество попыток, время обработки, результат и ошибки
- **VerificationHistory** — история успешно выполненных проверок: изображение, пользователь, дата и результат анализа
- **ModelVersion** — информация о версии ML-модели, используемых признаках и датасете
