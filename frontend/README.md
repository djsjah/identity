# I-Dentity Frontend

## Стек

- **React 19, TypeScript 5.7** — библиотека и язык приложения

- **Vite 6** — сборка и запуск приложения

- **MobX 6** — управление состоянием приложения

- **React Router 7** — маршрутизация между страницами

- **i18next, react-i18next** — поддержка русского и английского языков

- **Sass (SCSS Modules)** — стилизация компонентов



## Адрес

Если запускать с настройками по умолчанию:

- http://localhost:5173



## Запуск

Для запуска необходимы **Node.js 20.19+** и npm.

1. В корне проекта создать файл `.env` и скопировать в него содержимое `.env.example`

2. Открыть терминал в корне проекта и установить зависимости командой:

   `npm ci`

3. Запустить фронтенд через терминал в корне проекта командой:

   `npm run dev`

   Для Windows PowerShell:

   `npm.cmd run dev`

При стандартных настройках из `.env.example` Vite автоматически перенаправляет запросы `/auth`, `/users` и `/images` на бэкенд.

**Дополнительные команды:**

- `npm run build` — сборка приложения
- `npm run preview` — просмотр собранной версии
- `npm run lint` — проверка кода
- `npm run test` — запуск автоматических тестов



## Авторизация

Авторизация на фронтенде работает через **сессии и куки**.

1. При регистрации или входе фронтенд отправляет данные пользователя на бэкенд через `POST /auth/sign-up` или `POST /auth/sign-in`. Бэкенд создает сессию и устанавливает куки `IDENTITY_SESSION`

2. Браузер автоматически сохраняет куки и отправляет его при последующих запросах. За счет флага `HttpOnly` JavaScript не имеет доступа к токену сессии

3. При открытии или обновлении страницы `AuthStore` отправляет `GET /auth/me`, чтобы проверить действительность сессии и восстановить данные пользователя

4. При выходе отправляется `POST /auth/logout`. Бэкенд отзывает сессию, после чего `AuthStore` очищает данные пользователя

**Защита от CSRF:** перед каждым изменяющим запросом `apiRequest` (`src/api/client.ts`) получает CSRF-токен через `GET /auth/csrf` и передает его в заголовке `X-XSRF-TOKEN`.

Состояние авторизации хранится в `AuthStore` (`src/store/auth.ts`). Через настройки аккаунта пользователь также может изменить почту и пароль.



## Проверка изображений

Проверка изображений выполняется **асинхронно**. Фронтенд не ожидает завершения анализа в ответе на загрузку файла, а отдельно запрашивает состояние задачи.

1. **Выбор изображения.** Пользователь выбирает файл через `UploadButton`. Если пользователь не авторизован, вместо выбора файла открывается окно входа в систему

2. **Загрузка изображения.** `ValidationStore` (`src/store/validation.ts`) проверяет формат (JPEG/PNG) и размер файла (до 5 МБ), после чего отправляет его на бэкенд через `POST /images/upload` в формате `multipart/form-data`

3. **Создание задачи.** После успешного сохранения изображения бэкенд возвращает `202 Accepted` с идентификатором `imageId` и статусом `PENDING`. Фронтенд сохраняет полученный `imageId` и переходит к ожиданию результата

4. **Ожидание результата.** `ValidationStore` каждые **2 секунды** отправляет `GET /images/{imageId}/result`. Пока задача находится в `PENDING` или `PROCESSING`, на странице отображается индикатор загрузки. Повторно отправлять само изображение не нужно

5. **Отображение результата.** При статусе `COMPLETED` фронтенд получает результат классификации и вероятность подмены лица. На странице `ResultPage` отображается, является ли изображение подлинным (`Real`) или поддельным (`Fake`), а также вероятность выбранного класса в процентах. При статусе `FAILED` выводится сообщение об ошибке.

**Обработка ошибок и восстановление**

Если запрос результата временно завершается сетевой ошибкой, фронтенд повторяет его. После **пяти последовательных неудачных запросов** автоматический опрос прекращается, а пользователь может возобновить его кнопкой без повторной загрузки изображения.

Идентификатор `imageId` сохраняется в `sessionStorage`. Поэтому после обновления страницы фронтенд может восстановить опрос той же задачи, не создавая новую проверку. Сам файл изображения в `sessionStorage` не сохраняется.
